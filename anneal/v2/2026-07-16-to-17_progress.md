## Plan

1. Port the attribute schema parser into Anneal v2, without copying the rough prototype README.
2. Rename `tag`/`tags` syntax to `domain`/`domains`, with default domain `soundness`.
3. Use `syn::parse_quote!`-style tests for Rust attributes and Rust items instead of string-only parser tests.
4. Keep item-kind restrictions close to schema matching so unsupported combinations can be rejected early.
5. Add Aeneas invocation through the exocrate-provided toolchain rather than hard-coded paths.
6. Generate a Lean workspace using path-based dependencies into the exocrate-provided Aeneas Lean package.
7. Build theorem generation incrementally, starting with Lean-language function postconditions in the `soundness` domain.

## Current Status

- Implemented: attribute parser port as `src/annotations/`.
- Implemented: `domain`/`domains` syntax with default `soundness`.
- Implemented: parser tests based on `syn::parse_quote!`.
- Implemented: schema-level target restrictions for values and flags.
- Caveat: only Lean-language proposition values are supported initially; Rust-language propositions produce an explicit unsupported-value error.
- Implemented: Aeneas invocation through the exocrate-provided `aeneas` binary after Charon.
- Implemented: separate Lean output root with `--lean-output-dir`.
- Implemented: generated Lake workspace metadata with path-based dependencies into the exocrate-provided Aeneas Lean package and its package manifest.
- Implemented: default Lake build for generated Lean, with `--no-lean-build` as a debugging escape hatch.
- Implemented: Rust source scanning for `#[anneal]` attributes keeps supported function postcondition specs and fails clearly for unsupported soundness combinations.
- Implemented: default `Soundness.lean` generation for supported Aeneas `Result` functions as ordinary `@[step]` theorems. Unannotated functions use the default successful-return correctness shape `f args ⦃ result => True ⦄`.
- Implemented: first annotation-driven theorem generation slice for ordinary free-function Lean `ensures` clauses. Generated theorems assert annotated conditions as successful-result postconditions.
- Implemented: ordinary free-function Lean `requires` clauses as additional hypothesis arguments on the declaring function's generated step theorem. Generated code places a visible `/- -------------------- Anneal hypotheses -------------------- -/` separator between Rust arguments and Anneal hypotheses.
- Implemented: caller checking by emitting ordinary generated `@[step]` theorem attempts for every supported lowered function. If a caller body does not establish a callee precondition, the caller's generated `step*` proof fails to compile at that call-site obligation.
- Implemented: first-class Rust `#[anneal(...)]` annotations remain in user source while Charon runs against a derived source view with Anneal attributes stripped after scanning.
- Implemented: soundness-domain auxiliary Lean `theorem` annotations are emitted into `Soundness.lean` before generated obligations, including Lean attrs, args, types, and tactic/term proofs.
- Implemented: function `invariant` clauses are treated as both entry requirements and `ok` postconditions in the invariant-bearing function's generated `@[step]` theorem type. Callers prove invariant-as-precondition obligations through their own generated `step*` proof attempts, without inherited theorem-type hypotheses.
- Implemented: trait associated function specs are expanded to matching trait impl methods for simple non-generic trait/self names. Impl methods may provide proof-only annotations to discharge obligations inherited from the trait method.
- Implemented: initial struct invariant support for structs with private named fields. Struct invariants use `self` in the Lean proposition, are matched through Aeneas/LLBC type IDs, and currently generate obligations for direct `T` returns, direct `T`/`&T` arguments as preconditions, and single `&mut T` arguments as preconditions plus `result` postconditions. Nested occurrences are detected and rejected for annotated invariant types rather than silently ignored.
- Implemented: `examples/` as a standalone Cargo package with real `--example` targets for call-site preconditions, postconditions, function invariants, trait method preconditions, and struct invariants.
- Implemented: generated Anneal spec theorems use Aeneas' ordinary `@[step]` theorem shape, with Anneal requirements and invariant-as-precondition obligations emitted as theorem arguments and successful-result obligations emitted in `f args ⦃ result => ... ⦄`.
- Caveat: matching from Rust to Aeneas definitions is by function basename and must be unambiguous within the selected artifact.
- Caveat: the generated default proof still depends on Aeneas' `@[step]` database. Some primitive operations, such as checked scalar addition, expose safety side conditions through `step*`; source code that does not establish those conditions should produce generated Lean that fails to compile.
- Caveat: trait support does not yet cover subtraits, generic impls, trait bounds, associated types, or inherent impl annotations.
- Caveat: struct invariant support is intentionally narrow. It does not yet prove obligations for nested return/argument positions such as `Option<T>`, tuples containing `T`, `impl Trait`, `dyn Trait`, trait associated types, or multiple mutable-reference outputs; those are reported as unsupported when they involve an annotated invariant type.

## Notes

- The `step` branch in `aeneas_lowering_workspace` confirms the basic lowering order: run Charon with the Aeneas preset, run `aeneas -backend lean -split-files` over the generated LLBC, then create a Lake workspace that depends on the Aeneas Lean backend by path.
- The earlier attribute parser prototype used a backtracking schema matcher. The port should keep that design, but make the syntax Anneal-specific and prepare for item-type restrictions.
- The exocrate uprev currently makes the default Nix archive aliases use the slow, clean Aeneas build path instead of the fast cache-seeded path. The fast path reuses a prepared Lake cache, but this Aeneas pin refreshes Lake traces during the build, which invalidates that prepared cache. The slow path rebuilds Aeneas cleanly and is the correct default for now; the fast aliases remain in the flake so we can switch back after the upstream cache seeding strategy is refreshed for this Aeneas/Lake behavior.
